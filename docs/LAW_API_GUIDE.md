# 법제처 국가법령정보 OPEN API — 실측 규격

> 이 문서의 모든 수치는 **라이브 왕복으로 확정**했다(2026-09-08).
> 재현: `python scripts/probe_api.py all` · 그때의 실응답은 `tests/fixtures/*.xml`.
> 검증 등급 — ✅ 이 저장소가 직접 측정 · 📄 문서에만 있음 · ❓ 미확인.

## 0. 🔴 법제처 API 는 둘이고 서로 다른 물건이다

여기서 헷갈리면 반나절을 버린다. **둘 다 법제처 것인데 데이터가 다르다.**

| | data.go.kr 공유서비스 (1170000) | **법제처 OPEN API (DRF)** ← 이 저장소 |
|---|---|---|
| 인증 | `serviceKey` | **`OC`** |
| 범위 | 목록조회 **8종만** | 카탈로그 전부 |
| 본문 | **없음** | **있다** |
| 판례 | **없음** | 있다 |

공유서비스로는 **조문 본문도 판례도 못 얻는다.** 법령·판례를 인용하려면 DRF 다.

공유서비스를 쓸 일이 생긴다면 함정 둘(✅ 실측):
- `serviceKey` 를 **맨 앞에** 둬야 한다. 뒤에 붙이면 `NO_OPENAPI_SERVICE_ERROR`(12)
  "해당 오픈API 서비스가 없거나 폐기됨" 이 온다 — 방금 승인받은 키로 이 메시지를 보면
  **승인 실패로 오인한다.**
- `query` 도 필수다(생략 시 `HTTP_ERROR` 04).

## 1. 인증 — `OC` 는 비밀값이 아니다

`OC` 는 open.law.go.kr 에서 OPEN API 를 신청할 때 **가입 이메일의 @ 앞부분**으로
본인이 지정하는 식별자다. 요청 URL 에 평문으로 실리고, **응답의 `…상세링크` 에도
그대로 되돌아온다**(✅ 실측).

```
/DRF/lawService.do?OC=__OC__&target=law&MST=209959&type=HTML&mobileYn=&efYd=20190715
```

→ 그래서 `scrub()` 의 대상이 아니다. 지우면 사용자가 열 수 있는 링크가 깨진다.
다만 공개 저장소의 픽스처에서는 `__OC__` 로 가려 두었다(개인 식별자이므로).

✅ **갈래별 신청 범위가 없다.** 본인 OC 와 공용 시험계정(`test`)의 결과가 한 줄도
다르지 않았다(T41 실측). 즉 한 번 발급받으면 카탈로그 전부에 닿는다.

## 2. 엔드포인트

| 용도 | URL |
|---|---|
| 목록 | `https://www.law.go.kr/DRF/lawSearch.do` |
| 본문 | `https://www.law.go.kr/DRF/lawService.do` |

공통 파라미터: `OC` · `type=XML` · `target` · `query`(목록) · `display` · `page` ·
`search`(1=제목, 2=본문 포함).

## 3. 🔴 갈래(target)마다 태그가 다르고, 이름에서 유추할 수 없다

✅ 전수 실측. **규칙이 아니라 표다** — 지어내면 조용히 0건이 된다.

| target | 갈래 | 목록 루트 | 레코드 태그 | 식별자 필드 | 본문 파라미터 | 본문 루트 |
|---|---|---|---|---|---|---|
| `law` | 현행법령 | `LawSearch` | `law` | 법령일련번호 | **`MST`** | `법령` |
| `eflaw` | 시행일법령 | `LawSearch` | `law` | 법령일련번호 | `MST` **+ `efYd`** ⚠ | `법령` |
| `elaw` | 영문법령 | `LawSearch` | `law` | 법령일련번호 | `MST` | **`Law`** ⚠ |
| `admrul` | 행정규칙 | `AdmRulSearch` | `admrul` | 행정규칙일련번호 | **`ID`** | `AdmRulService` |
| `ordin` | 자치법규 | `OrdinSearch` | **`law`** ⚠ | 자치법규일련번호 | `MST` | `LawService` |
| `prec` | 판례 | `PrecSearch` | `prec` | 판례일련번호 | `ID` | `PrecService` |
| `detc` | 헌재결정례 | `DetcSearch` | **`Detc`** ⚠ | 헌재결정례일련번호 | `ID` | `DetcService` |
| `expc` | 법령해석례 | **`Expc`** ⚠ | `expc` | 법령해석례일련번호 | `ID` | `ExpcService` |
| `trty` | 조약 | `TrtySearch` | **`Trty`** ⚠ | 조약일련번호 | `ID` | `BothTrtyService` |
| `lsStmd` | 법령체계도 | `LsStmdSearch` | **`law`** ⚠ | 법령일련번호 | `MST` | `LsStmd` |

**함정 일곱:**
1. `ordin`(자치법규)의 레코드 태그는 **`<law>`** 다. 제 이름이 아니다.
2. `lsStmd`(법령체계도)의 레코드 태그도 **`<law>`** 다 — 같은 함정.
3. `detc`·`trty` 는 **대문자로 시작**한다(`<Detc>`·`<Trty>`). XML 태그는 대소문자를
   구분하므로 정규화하면 0건이 된다.
4. `expc` 의 목록 루트는 **`<Expc>`** 로, 혼자만 `…Search` 접미가 없다.
5. 본문 파라미터가 **`MST`(법령·자치법규)와 `ID`(나머지)** 로 갈린다.
6. 🔴 `elaw`(영문법령)의 **본문 루트는 `<Law>`** 인데, 이것은 '없음' 봉투의 루트와
   **똑같다**(§4). 자식이 있는지로만 구분된다 — 텍스트만 보고 판단하면 19KB 짜리
   정상 본문을 '없음'으로 버린다. 본문 구조도 다르다
   (`InfSection`·`JoSection`·`ArSection`·`BylSection`).
7. 🔴 `eflaw`(시행일법령) 본문은 **`MST` 만으로는 HTML** 이 온다(1,649B).
   `efYd`(시행일자)를 함께 줘야 XML(317KB)이 온다. 시행일법령은 같은 법령의 시행일별
   판본이라 **(MST, efYd) 한 쌍이 문헌의 신원**이다 — 실제로 목록에 같은
   법령일련번호가 `시행예정`·`현행`·`연혁` 으로 여러 줄 나온다.

⚠️ 1~7 은 전부 **짐작하면 틀리는 것들**이다. 이 저장소의 초판은 `eflaw`·`elaw`·`lsStmd`
가 `law` 계열과 같으리라 짐작했고 **셋 다 틀렸다** — `scripts/probe_api.py envelopes`
가 잡았다. 그래서 이 표는 규칙이 아니라 **측정 결과**다.

## 4. 🔴 모든 실패가 HTTP 200 이다

✅ 실측. **상태코드로는 아무것도 알 수 없다.**

| 상황 | HTTP | 본문 |
|---|---|---|
| 없는 `target` | **200** | **0바이트** (Content-Type 도 없음) |
| 잘못된 `OC` | **200** | `<Response><result>사용자 정보 검증에 실패하였습니다.</result><msg>…IP주소…</msg></Response>` |
| `OC` 누락 | **200** | `<Response><result>필수입력요소 검증에 실패하였습니다.</result>…</Response>` |
| 없는 식별자 | **200** | `<Law>일치하는 법령이 없습니다.  법령명을 확인하여 주십시오.</Law>` |

마지막이 특히 위험하다 — **`target` 과 무관하게 루트가 `<Law>`** 다. 판례를 조회해도
`<Law>일치하는 판례가 없습니다</Law>` 가 온다. 기대 루트(`PrecService`)만 찾으면
'본문이 비어 있다'로 둔갑한다.

### 4-1. 🔴 `query` 를 빼면 전체 카탈로그가 온다

오류가 아니다. ✅ 실측: `target=law` 에 `query` 없이 호출하면
`<키워드>*</키워드>` · `totalCnt` **5,614**(현행법령 전량)가 온다. `query=교육` 은 159건이다.
→ 이 서버는 **빈 검색어를 거부**하고, 전량이 필요하면 `query="*"` 를 명시하게 한다.

## 5. 상한 — 자매 API 의 사실을 이식하지 말 것

✅ 실측(`ordin`, '교육' 8,517건을 자로 사용).

- **`display` 상한은 500.** 1000을 요청하면 오류가 아니라 조용히 500으로 깎이고,
  `numOfRows` 는 500을 에코한다.

  | 요청 display | numOfRows 에코 | 실제 레코드 |
  |---|---|---|
  | 100 | 100 | 100 |
  | 300 | 300 | 300 |
  | 1000 | **500** | **500** |

- ⚠️ **`numOfRows` 는 요청한 페이지 크기가 아니라 실제로 돌려준 건수다.**
  `display=100` 인데 결과가 3건이면 `numOfRows=3` 이다. 이걸 '서버가 깎았다'로 읽으면
  결과가 적을 때마다 거짓 경고가 나고, 페이지 크기를 3으로 줄여 이후 페이징이 기어간다.
  **진짜 절삭은 `에코 < 요청` 이면서 `totalCnt > 에코` 일 때뿐이다.**

- 🔴 **`page` 에는 하드 상한이 없다.** 국회도서관의 `pageno<=99`(회수 한계 99,000건)를
  이식하면 안 된다.

  | page | 레코드 | 비고 |
  |---|---|---|
  | 2 | 100 | |
  | 50 | 100 | |
  | 86 | **17** | 8,517/100 의 마지막 페이지 |
  | 200 | 0 | 끝을 지나면 정상적으로 빈다 |

  → **`totalCnt` 전량을 회수할 수 있다.** 절단은 오직 우리가 거는 예산 때문이다.

## 6. 본문 — 🔴 알맹이는 `조문내용` 이 아니라 `항`·`호` 안에 있다

✅ 실측(감사원규칙, 조문단위 39개):

| 태그 | 개수 | 내용 |
|---|---|---|
| `조문내용` | 39 | 조 표제 문장뿐 — "제3조(교육대상) … 대상으로 한다." |
| `항` | 36 | 실제 규정 |
| `항/호` | 21 | 각 호 |

`조문내용` 만 읽으면 **본문의 70%를 잃는다**(2,057자 / 실제 7,359자). 오류는 나지
않는다 — 조용히 줄어든다. 이 저장소의 초판이 실제로 그랬고 회귀 테스트로 고정했다.

### 6-1. 조문 구조는 갈래마다 태그 이름이 다르다

```
법령      <법령><조문><조문단위>  조문번호·조문제목·조문내용·조문여부·조문가지번호·항
자치법규   <LawService><조문><조>  조문번호·조제목·조내용·조문여부        ← 이름이 다르다
```

- `조문여부='전문'` 은 **장·절 표제**이지 조문이 아니다.
  ✅ 실측: 초·중등교육법 = 조문 119 + 표제 16 = **135**(T41 의 "조문단위 135개"와 일치).
- `조문가지번호` 는 제6조의**2** 를 뜻한다 — 인용 위치 표기에 필요하다.
- `기본정보/연락부서/부서단위/부서명` 처럼 **3단 중첩**이 있다. 한 단만 훑으면 사라진다.
- 행정규칙은 `조문형식여부='N'` 이면 조문 구조가 없고 `조문내용` 한 덩어리로 온다.
  별표·서식은 **`첨부파일`**(첨부파일명·첨부파일링크)로 따로 온다 — 버리면 원문에 못 닿는다.

### 6-2. 🔴 판례 본문은 데이터출처에 따라 없다

✅ 실측. 같은 목록에서 나온 두 건인데 결과가 갈린다:

| 데이터출처명 | 본문 조회 |
|---|---|
| `대법원` | ✅ `PrecService` 18KB (판시사항·판결요지·판례내용·참조조문) |
| `국세법령정보시스템` | ❌ `<Law>일치하는 판례가 없습니다</Law>` |

목록에는 나오는데 본문이 없다. **오류가 아니라 결손**이므로, 수집기는 기록하고
넘어가야 한다. T41 은 "prec 본문 확인"이라고만 적었는데, 맞지만 전부는 아니다.

## 7. 🔴 같은 필드가 목록과 본문에서 다른 꼴로 온다 (날짜)

✅ 실측.

| 필드 | 목록 | 본문 |
|---|---|---|
| 판례 `선고일자` | `2026.04.23` | `20260212` |
| 헌재 `종국일자` | `2016.10.27` | `20161027` |
| 법령 `공포일자` | `20190715` | `20190715` |

한쪽만 보고 파서를 쓰면 다른 쪽에서 조용히 빈 값이 된다. 이 저장소는 두 꼴을 모두
받아 `YYYY-MM-DD` 로 정규화하고, **모르는 꼴은 원문 그대로 둔다**(비우면 사라진다).

## 8. 🔴 텍스트의 꺾쇠는 HTML 이 아닐 수 있다

법령 텍스트는 `<`·`>` 를 **내용으로** 쓴다:

```
제1조(목적) … 정함을 목적으로 한다. <개정 2010.7.6>
부칙 <2010.7.5> 제1조(시행일) 이 조례는 …
```

임의의 `<...>` 를 지우면 개정 이력과 부칙 일자가 통째로 사라진다. 자매 저장소
(na-openapi-mcp)가 정확히 이 실수로 표제 18건을 손상시켰다.
→ **알려진 HTML 태그 이름만** 지운다(`br`·`p`·`img`·`div` …).

실제로 마크업이 섞이는 자리(✅ 실측): 판례 `판시사항`·`판결요지` 는 `<br/>` 로 시작하고,
행정규칙 `조문내용` 에는 `<img id="149458663">` 가 박혀 있다.

## 10. XML 을 주지 않는 target

✅ 실측 — 문서가 아니라 응답으로 확인했다.

| target | lawSearch.do | lawService.do |
|---|---|---|
| `lsHistory`(법령 연혁) | 200 **text/html** 21KB | 200 **text/html** 1.6KB |
| `couseLs`(관련법령) | 200 **text/html** | **HTTP 404** |

`type=XML` 을 무시한다. 둘 다 화면용 연계 정보이지 인용 가능한 문헌이 아니므로
이 저장소의 범위 밖이다. **T41 이 '미해결'로 남긴 것인데, 미해결이 아니라
'XML 미지원'이 사실이다.**

## 11. ❓ 남은 미확인 — 부처 1차 법령해석 target 코드

open.law.go.kr 의 안내 목록에는 부처 40여 곳(교육부·고용노동부·국토교통부…)의
법령해석 API 가 실려 있으나 **코드 값이 적혀 있지 않다.** 안내 페이지가 자바스크립트로
그려져 본문만 받아서는 링크(`htmlName` 파라미터)를 얻을 수 없다(✅ 확인).

T41 이 후보 9개(`moe`·`moel`·`moleg` …)를 시도해 전부 빈 응답이었다.
**더 짐작하지 말 것** — 브라우저로 안내 페이지를 열어 링크를 봐야 한다.

당장 막히지는 않는다. 법제처 유권해석은 `expc` 로 조회되고 '교육' 579건이 나온다.
